# CLAUDE.md — Phone LiDAR

iPhone LiDAR scanner (SwiftUI, iOS 17+, iPhone only; target iPhone 17 Pro Max). Modes: Room (RoomPlan),
Equipment mesh (ARKit), Object capture (RealityKit), and Line scan: a fixed phone above moving material (OSB mat or
board) recording LiDAR depth + video, measuring speed, and building a topographic map, statistics and a real-time replay.

## Hard constraints
- No Mac and no local Swift toolchain. Never try to compile or run Swift here. GitHub Actions is the compiler.
- The Xcode project is generated by XcodeGen from `project.yml`. Never commit an `.xcodeproj`.
- LiDAR, RoomPlan, ARKit scene reconstruction, Object Capture and AVFoundation LiDAR depth only work on a physical
  iPhone. The simulator runs pure logic only; keep device-only code out of the test target.
- Builds stay warning-free (0 warnings). A new warning is a defect to fix, not to suppress.
- Public repo: never commit secrets, Apple IDs, keys, certificates, profiles, personal data, local paths, plant
  photos/video, recordings or scan data. Look-reference media stays in the owner's local folder.
- Keep on-disk formats readable by new builds (docs/design.md §7). New persisted `Codable` fields are Optional;
  a binary layout change bumps the version and keeps the old reader.
- Push only your own branch. Never push to `main`. Do not merge PRs unless the orchestrator asks.

## Build and test
- CI workflow `Build iOS app` (`macos-26`, Xcode 26.x), on every pull request into `main`, on pushes to `main` that
  change more than `*.md`, and by hand. Job `unsigned-ipa`: `xcodegen generate` (pinned release) → unsigned Release
  build with warnings as errors plus a log gate → artifact `PhoneLidar-unsigned-ipa-<run>`; `build-log-<run>` holds
  the full log. Build number = run number. Actions and tools are pinned; the token is read-only.
- Unit tests: scheme `PhoneLidarTests`, CI job `unit-tests` on the newest iPhone simulator (warnings fail it;
  `unit-test-results-<run>` is kept on failure). The test target compiles the pure-logic files listed in
  `project.yml`; add a file there when it gets tests. The optional `testflight` job needs both jobs.
- `gh` works through the REST API only (no GraphQL):
  ```
  gh workflow run "Build iOS app" -R AliG1111/PhoneLidar --ref <branch>
  gh run list -R AliG1111/PhoneLidar --branch <branch> -L 3
  gh run watch <id> -R AliG1111/PhoneLidar --exit-status     # or poll: gh run view <id> -R AliG1111/PhoneLidar
  gh run view <id> -R AliG1111/PhoneLidar --log-failed
  ```
- Reading failures: the run summary page lists `error:` lines (and warning counts); `--log-failed` gives the failing
  step; download `build-log-<run>` / `unit-test-results-<run>` for the full log or `.xcresult`. Fix the first error first.
- Git proxy allows 2 concurrent transfers for this repo; on HTTP 429 wait 5 s and retry once.

## Workflow and definition of done
1. Branch from the latest `main` (`git switch -c <topic> origin/main`), one topic per branch.
2. Small commits at each verified unit of work; imperative subject; trailer below.
3. Self-review with the checklist in docs/implementation-plan.md §4 at the same model/level.
4. CI green: app build and unit tests, 0 warnings. Add or update unit tests for changed pure logic.
5. Open a PR into `main` with summary, FR-/NFR- IDs, finding IDs, CI run number.
6. After merge: tick the task and add a change-log entry in docs/implementation-plan.md; update requirements
   traceability/status and design when behaviour or formats change; list user-visible changes for the build guide.
   `REVISIONS.md` and the owner's local copy are handled by the orchestrator. Keep this file current.

## Review protocol
- Severity: Critical (crash, data loss, privacy exposure, wrong measurement in output files) › High (wrong results in
  common use, thread-safety bug, leak during capture, CI break) › Medium (edge-case errors, missing error handling,
  performance that affects use) › Low (maintainability, polish).
- Cycle: review → triage → fix → CI green → re-review changed code and neighbours; repeat until a review yields
  no new findings of any severity (owner's rule). Critical/High/Medium are always fixed; a Low is fixed or, if
  risky or large, logged in the P10 backlog with a reason. CI green at a branch head before any merge.
- Reviewers are fresh agents (Opus 5.5 / high); final review Opus 5.5 / max. Record each cycle in
  `docs/reviews/<YYYY-MM-DD>-<milestone>.md` (ID, severity, file:line, summary, status).

## Coding conventions
- Units: line scan works in millimetres, mm/s, seconds and degrees (internally and in files); Room/Mesh/Object use
  metres from Apple frameworks. Put the unit in the name or a doc comment (`medianDepth` is mm, `time` is s).
- Orientation conventions (design §6.1): buffers stay in sensor landscape; buffer x/depth u = across = top → bottom of
  the portrait screen; buffer y/depth v = along = right → left; `TravelDirection.bufferSign`; speeds + = travel
  direction; zones n = row·6 + column via `ZoneGrid`. Reuse these helpers instead of re-deriving mappings.
- Formatting: user text via `Units` (m + ft-in, m² + ft²) and `SpeedText` (mm/s, m/min, ft/min); file numbers via
  `String(format:)` (never localized). CSV through `CSV.make` (escaping, LF, trailing newline); large CSVs through
  `TextFileWriter`. JSON through `JSONEncoder.pretty` / `JSONDecoder.iso`. Write metadata with `.atomic`.
- File names are fixed constants (`Recording.json`, `Depth.bin`, `TopoGrid.bin`, `Baseline.bin`, …); scan folders are
  `<kind>_<yyyy-MM-dd_HHmmss>` from `ScanStore.newFolder`. Document every new file in design §7 and the build guide.
- Threading: UI and `@Observable` models are `@MainActor`. Per-frame line state lives on `phonelidar.line.data`;
  session control on `phonelidar.line.session`. Cross to the UI with values via `Task { @MainActor }`. Heavy work
  (map build, replay preparation, probe sampling) runs in `Task.detached` returning `Result`. Nothing blocking in the
  replay display-link tick. Tear down display links, observers and timers on disappear; check cancellation after
  `await` before starting work. Mark types `@unchecked Sendable` only when immutable or queue-confined, with a comment.
- Errors: user-facing `LocalizedError` (`ScanError`, `LineError`); no `try?` on paths that write or read measurement
  data; never delete captured data on failure.
- New scan mode: add a `ScanKind` case (title, SF Symbol), a Home row with a capability check, a full-screen capture
  view that saves via `ScanStore.newFolder` + `ScanStore.save(ScanRecord)` and calls `onFinish(id)`, and a section in
  `ScanDetailView` for mode-specific screens.
- Keep files focused (split beyond ~800 lines), doc comments on non-obvious maths, no third-party packages without a
  design decision, no force unwraps on file or device data, no debug `print`.
